# AI 投研｜公司估值、季报复查与 GitHub 发布操作规范（SOP）

> **文档性质**：人和 AI 助手均可执行的仓库更新规范，不是某家公司的投资结论。  
> **首次制定**：2026-10-23（北京时间）；**SOP 版本**：v1.0。  
> **适用仓库**：[moliq1/ai-investment-research](https://github.com/moliq1/ai-investment-research)；默认分支 \`main\`。  
> **优先级**：每次操作以仓库当时真实文件、代码、测试和最新公告为准；如本 SOP 与实际实现冲突，应先核对并更新 SOP，不得假设旧约定永远有效。

## 0. 一分钟速查：每次操作都要完成什么

**标准顺序**：拉取最新仓库 → 核验公司公告及收盘行情 → 对比上版预测 → 更新估值及说明 → 更新主 MD 与季度档案 → 校验 → 提交 → 查看 Actions 成败 → 核对网页。

五项不可妥协的规则：

1. **事实与推测分开**：公司公告的已实现数据、管理层指引、券商一致预期、自己的情景预测，分别标识来源、日期与口径；未知值不编造。
2. **估值与行情分开**：网页研究数据仅以主 MD 为准；最新有效收盘价由行情 JSON 单独维护。行情每日变化 ≠ 每日重新估值。
3. **当前版与历史版分开**：主 MD 总表和公司正文显示最新有效模型；在正文追加变更对照；每个财报季度另存不可静默覆盖的独立报告；Git 提交保留完整差异。
4. **A/H 统一股本与归母利润**：同公司同一经济权益使用同一估值模型，分市场显示本币价格与相应每股价值；区分合并利润/归母利润/少数股东权益，避免子公司重复估值。
5. **发布成功以网页部署为准**：仅有 Git commit 不代表 GitHub Pages 已更新。必须检查 Python、Node、Build、Deploy 都成功，再检查实际页面。

## 3. 分析之前的材料核验与证据优先级

1. **官方一手资料优先**：公司公告、交易所、巨潮/港交所披露、正式产量指引、矿山项目与并购公告；研究中记录公告标题、发布日期、URL、报告期及关键口径。无法读取原文须标记“未核验”，**不得转述为已核实**。
2. **财务事实**：营业收入、归母/扣非、经营现金流、CapEx、净债务、股本、归母净资产、期内变动、少数股东损益。对 A/H 股票区分会计币种与股票交易币种。
3. **产业经营**：价格、产量、销量、产能、单价、单位成本、项目投产/达产、重大并购。矿产量与权益量、合并口径与归母权益不可混同。
4. **市场与外部预期**：分别查 A/H 已完成交易日的收盘价、时间、币种、来源及合理汇率；金融数据可能滞后，应交叉核验。机构共识必须列“统计日期/样本数/预测年度”，不能称之为管理层承诺。
5. **旧预测快照**：先读主 MD 中现有模型、相关 \`reports/<slug>/\` 季报、必要时读历史 Git commit，然后再修改，防止事后篡改“当时预测”。

**时间规则**：报告期结束日、财报实际披露时刻、研究修订日、A/H 价格收盘日期、汇率参考日期分别记录。**晚间披露的三季报与当天收盘价存在时间先后差，不能说股价已反映财报**。A/H 休市不同步时，两只证券分别标注实际各自的最近完成交易日，禁止假设日期相同。

## 4. 首次公司估值：标准执行流程

### 4.1 建立假设和估值底稿

优先回答：3–5 年业务增长是否真实、利润和 FCF 是否可持续、当前价隐含何种盈利、我们的预期差来源、下行风险与兑现时间。对周期矿业公司：

- 金/铜/银等金属分别列悲观、基准、乐观**年度平均价格**及单位；不要把一个单日现货价混成全年平均价格。
- 每种矿产分别给产量和归母权益假设，逐项目列新增产能、并表时点、达产率、成本与关键条件；如未逐矿山建模，**必须明示仅为组合情景而非精确损益桥**。
- 区分**公司原指导 / 自己预测 / 券商一致预期**；如单个季度偏离指引，应调整自己的预测，不能擅自写“公司已下调指导”。
- 估值方法明示：PE、DCF、NAV、EV/EBITDA 或组合。对每个情景保留归母利润/FCFF、估值乘数或 WACC、股本、汇率、单位、估值时点及四舍五入规则。
- 写**反向估值**：当前股价在指定倍数或折现率下反推的可持续盈利/增长；与自己基准假设比较。
- 至少给出三条可证伪的验证指标和失效条件；高景气周期利润必须作均值回归压力测试。

### 4.2 主 MD 12 列估值总表

主表是网页和行情脚本的解析接口，**维持准确的列序和 12 列**：

\`公司 | 代码 | 行业 | 市场 | 价格基准日 | 参考股价 | 估值年份 | 悲观估值（每股） | 基准估值（每股） | 乐观估值（每股） | 估值方法 | 最近更新\`

- A 股代码使用 \`601899.SH\`、\`000807.SZ\`；港股使用零补齐的 \`02899.HK\` 等 **5 位**代码。网页行情映射上海 \`.SH → .SS\`、深市 \`.SZ\`、港股 \`02899.HK → 2899.HK\`。
- **一只证券一行**；同一家公司 A/H 用两行，币种分别 \`¥\` / \`HK$\`；正文可共用同一公司章节。
- 行业按当前主 MD 的行业分组；行业内部按“最近更新”**日期降序**；若新增行业，先核对前端显示与现有测试的行业列表，不要强行塞入错误分类。
- 总表内三档必须都是**有数值的完整情景**；不能留“待补充/待核实/示例”；每股区间下限 ≤ 上限，且与正文完全一致。
- 禁止在总表单元格随意插入竖线 \`|\`、增加换行或删改列数。更新日期时只改相应证券的参考日/模型日，不误改其他公司历史价格。
- 仅在**确实重新核验模型**时更新“最近更新”；自动刷新行情不等于模型重算。

### 4.3 公司正文的机器可读结构

公司章节形如：

\`\`\`markdown
### N. 公司名称（601899.SH / 02899.HK）
**当前估值快照：vX.Y｜YYYY-MM-DD**

#### 2.1 业绩锚点、现金流和当前估值
...（实际/预测/报告期/来源，清楚区分）...

#### 2.2 三情景参数与估值结果（2027E）
| 假设项目 | 悲观情景 | 基准情景 | 乐观情景 |
|---|---:|---:|---:|
| 2027E归母净利润（亿元） | ... | ... | ... |
| 合理PE（倍） | ... | ... | ... |
| **A 股每股估值（人民币）** | **¥...** | **¥...** | **¥...** |
| **H 股每股估值（港元）** | **HK$...** | **HK$...** | **HK$...** |

#### 2.3 核心估值逻辑
...

#### 2.4 反向估值与市场预期差
...

#### 2.5 估值与市场预期差的核验节点
...

#### 2.6 季度财报更新记录（按披露日倒序）
...

#### 原始聊天与研究来源

\`\`\`

解析器会寻找**含有“三情景参数与估值结果”的四级标题**，并在下面的 4 列参数表提取估值；会按正文中证券代码匹配 A/H 公司章节。正文建议保留“核心估值逻辑”“反向估值”“核验节点”“原始聊天与研究来源”等标题，以便网页完整展示并通过自动测试。

不要为每次季报新建 \`### N. 同公司...\`，否则会导致重复解析或旧模型抢占。公司详细季度历史放独立报告。若必要调整现有标题与表格语法，**必须同步修改解析器、测试与 SOP**。

## 5. 季报复查：标准流程（每季重复）

### 第一步：先冻结上版预测

记录上版发布日期、价格基准、核心产量/利润/FCF假设、三情景上下限、合理倍数、股本/汇率与原始 Git commit。**先固定旧值，再看新财报**，才能计算真实预测误差，不能用新观点重写旧假设。

### 第二步：拆分实际业绩

至少比较以下维度：

| 维度 | 必须比较的内容 |
|---|---|
| 增长 | 本季、累计 YTD、去年同期、上季：营收、归母、扣非、EPS |
| 质量 | 经营现金流、CapEx、简化 CFO−CapEx、营运资本、净负债、ROIC/ROE、少数股东权益 |
| 经营 | 分产品价格/产量/成本、毛利率、利润率、重点矿山或产线的达产进度 |
| 指引 | 年初指导 vs YTD实际 vs 剩余季度必须完成值；公告是否**正式修订指导** |
| 资本配置 | 并购、资产出售、分拆上市、分红、回购、融资、债务和股本变动 |
| 来源 | 报告期、披露时刻、官方链接、重要附注；外部机构预期须注明其统计时间 |

**计算检查**：
- \`当季单独值 = 本年YTD累计 − 本年上季末YTD累计\`，先核对财报是否直接公布单季值；
- \`TTM归母净利 = 上年全年归母净利 − 上年同期YTD归母净利 + 本年YTD归母净利\`；
- \`全年达标剩余产量 = 公司全年指导 − 已实现YTD\`；\`剩余需环比增长 = 剩余要求 / 最近完整季产量 − 1\`（写明这只是数学门槛）；
- \`简化FCF = CFO − 购建长期资产等现金支出\`，**不等于归母FCFE**；并购对价、融资、少数股东现金分配等应另看；
- \`现价隐含年归母利润 = 每股价格（统一人民币）× 总股本 / 假定前瞻PE\`；在 H 股上先统一汇率。
- \`A股相对H股溢价 = (A股人民币价 / (H股港元价 × 港元兑人民币汇率) − 1)×100%\`，\`H股相对A股折价 = 1 − H股折人民币价/A股价\`；**两者分母不同，不能写成同一百分比**。
- \`理论每股价(CNY) = 归母净利(亿元) × PE / 总股本(亿股)\`；\`理论每股价(HKD) = 理论每股价(CNY) / 汇率(CNY/HKD)\`。

### 第三步：回答“旧预测为什么错了？”

形成一张最小可追溯对照表（下面是**格式模板，不是事实**）：

| 指标（单位与时点） | 上期预计 | 本期实际 | 更新后的预测 | 变化原因 / 证据 |
|---|---:|---:|---:|---|
| 当季归母利润（亿元） | 旧预测 | 财报实际 | — | 价格、销量、成本、汇率、少数股东 |
| 全年矿产量（吨/万吨） | 旧模型 | 累计实际 | 新全年范围 | 项目投产/停复产/并表 |
| 下一年归母利润（亿元） | 旧基准 | — | 新基准 | 收入/利润率/资本配置变化 |
| 下一年每股基准估值 | 旧区间 | — | 新区间 | **利润变化 / PE变化 / 股本汇率变化分别列示** |

把“业绩好但不及此前极高预期”“盈利好且现金流好”“受一次性因素影响”分开论证。若证据不足，不强行上调或下调目标价；可以写**基准假设暂不变 + 下一验证点**，但季度档案仍应新增。

### 第四步：先保存独立的季度快照

默认路径 \`reports/<slug>/YYYYQn.md\`，建议保持下列结构：

\`\`\`markdown
# 公司名（证券代码）YYYYQn 季报复查与估值修订

> 报告期：...；财报披露时间：...；研究日：...；
> 收盘价格日期（A/H分别列出）：...；快照版本：YYYYQn-v1；
> 财报原文链接：...；模型性质：独立研究/非券商共识。

## 一、本季与累计业绩事实（官方披露）
...（实际、同比、环比、归母、扣非、现金流、产销、项目进度）...

## 二、上版预测与本季实际对照
...（旧预测、实际、偏差、主要成因）...

## 三、最新盈利与三情景估值
...（价格/销量/利润/PE或DCF、币种、股本、汇率、A/H区间）...

## 四、风险、失效条件与下期核验
...（何时复查，什么数据会推翻当前判断）...

## 五、来源和版本
...（公告原文、行情、机构预期、原始模型Git提交、修订日）...
\`\`\`

如财报更正，应更新文件顶部 \`YYYYQn-v2\` 与“更正记录”，用 Git 比较保留 v1，**不能静默改写原值**。文件中的年份季度用**财务报告期**，而不是报道文章发布月份。

### 第五步：将精简版同步回主 MD

1. 修改总表对应证券行（参考价日期、当前估值、研究更新日、方法）；公司 A/H 同时更新估值，**股票报价可因停市采用不同收盘日期**。
2. 修改该公司的**同一个**正文：最新业绩、现价估值、三情景参数/每股结果、反向估值、关键风险和节点。
3. 在 \`#### 季度财报更新记录（按披露日倒序）\` 前面加入本季的“旧版→新版”紧凑表，并链接新季度档案；更早的完整说明仍在历史文件和 Git 提交中。
4. 主 MD 顶部文档版本按规则升级（例如 v2.3→v2.4），在底部 \`## 四、变更记录\` 新增一条：日期、公司、版本、更新内容。
5. 复查同一行业内“最近更新”排序；如日期变化导致排序错误，**连同正文公司章节位置**一起调整且保留标题序号连续。

**不要把季度报告全文无节制地贴到主 MD**：现在网页直接渲染公司正文，长文会令页面难读；主文保留当前模型和最关键对照，细节在 GitHub \`reports/\`。独立季报链接**不是网页会自动展开的源数据**；若希望在网站上显示历史季度目录，需要单独开发功能并测试。

## 6. 真实示例：紫金矿业 2026Q3 的改动记录

- 旧版 \`v2.3\`（2026-10-22）：A股基准 **¥30.5–41.4**，H股基准 **HK$35.6–48.3**；2027基准归母利润 **900–1,000亿元**。
- 三季报后 \`v2.4\`（2026-10-23）：基准利润改为 **840–940亿元**，A股基准 **¥28.4–38.9**，H股基准 **HK$33.2–45.4**；A/H参考收盘分别为 **¥28.79、HK$29.06**（均为财报当晚披露前的收盘）。
- 主要修订原因：前三季度矿产金/铜完成率较低、Q3盈利边际较H1平均放缓；同时记录赤峰黄金控制权收购对未来并表的可能影响，**没有把期后收购计入Q3已实现利润**。
- 主 MD：\`sources/AI投研_公司估值情景汇总.md\` 的紫金公司章节及A/H两行；独立季报：[reports/zijin-mining/2026Q3.md](../reports/zijin-mining/2026Q3.md)。
- 对照版本： [v2.3 最初提交](https://github.com/moliq1/ai-investment-research/commit/ad280d155c37bd44407f8ffc63b558f876d34799) → [v2.4 更新提交](https://github.com/moliq1/ai-investment-research/commit/d532b3d840a1707fe5df2d988c197f6d467ab7ab)。

此例用于说明**如何留痕**，不是要求后续所有公司的利润修订幅度、PE或金铜价格都相同。

## 7. GitHub 更新及发布验收（必须执行）

### 7.1 改动前

- 获取最新 \`main\` 分支，不要沿用聊天里保存的旧 SHA / 文件内容；检查是否已有同名季度档案、同类变更或其他人正在修改。
- 修改范围尽量局限于主 MD、当期季度档案以及必要的 README/测试/解析器；不覆盖其他公司的研究，不能顺便用旧行情替换新行情。
- 建议一次 Git commit 同时包含互相依赖的“主 MD + 季报报告”，避免主表先发布但季报链接不存在。
- GitHub API 写入时先获取最新 blob SHA/branch head，发生冲突则重新拉取并合并，**禁止强推覆盖**。
- 需要使用 PR 审核时先走独立分支、通过 CI 后再合并；直接写 \`main\` 时必须有更严格的提交后校验。

### 7.2 本地验证命令

在仓库根目录执行：

\`\`\`bash
python -m unittest discover -s tests -v
node --check assets/research.js
node tests/smoke_research.js
python scripts/build_site.py
\`\`\`

建议额外手工检查：每行恰有12列、总表证券无重复、行业及日期排序、章节能匹配证券、三情景总表与正文币种/数字相符、A/H换算误差合理、原始来源可访问、没有把待核实数字写成实际。

**警惕真实失败案例（2026-10-22）**：第一次新增紫金A/H后，自动测试仍写死“v2.2”和“12条记录”，网页解析器还不认识 \`（601899.SH / 02899.HK）\` 合并章节，导致 Pages 构建失败。后来同步改测试与解析器，才部署成功。以后**不能因新增公司/章节/版本便再写死总条数**；必须让测试验证结构与真实主表一致。

### 7.3 提交及发布后

1. 检查 [GitHub Actions](https://github.com/moliq1/ai-investment-research/actions) 最新的 \`Publish research dashboard\`（或计划更新 \`Refresh Markdown valuation-universe quotes and publish site\`），确认对应提交已执行，所有校验、Build 和 \`Deploy Pages\` 结果为 **success**。
2. 打开 [网站首页](https://moliq1.github.io/ai-investment-research/) 和对应公司页（如 [紫金A](https://moliq1.github.io/ai-investment-research/#/company/601899.SH)、[紫金H](https://moliq1.github.io/ai-investment-research/#/company/02899.HK)）。核对**文档版本、公司数量、悲观/基准/乐观值、公司详情表、研究更新时间**。
3. 确认主 MD、报告文件的 GitHub 链接都存在；报告目录可访问，但目前**不会被静态构建直接复制到网页**。
4. 核对 \`data/market_quotes.json\` 中新增证券是否有记录，且 \`closeDate\` 是各自市场最近的有效已完成交易日。缺或过期要显示缺数据，不应篡改主 MD 的研究参考价。
5. 若 Actions **failure**，先点开失败任务中的步骤及日志；优先检查 Python/Node 测试、表格语法、正文标题、行情覆盖、数据源失败与 Pages 环境。修复后重新部署，未成功前只能说“文件已提交，**网页尚未更新**”。
6. 即使 Actions 成功，浏览器仍旧时再尝试硬刷新/无痕窗口，同时确认页面真正载入最新版本；不要先归因于缓存。
7. 最终向用户报告：**研究结论及关键变化、写入的文件路径、Git commit 链接、CI/Pages结果、网页直达链接、未核实事项**。不要在未核验时声称“已更新网页”。

**行情自动刷新注意**：\`pages.yml\` 推送流程会检查并在必要时写回行情 JSON；\`quotes.yml\` 的 \`GITHUB_TOKEN\` 提交不一定触发另一条 push workflow，故其自身还会直接部署。后续若有机器人行情提交使 \`main\` HEAD 变化，比较**研究提交与 Pages 运行**时应同时检查真正发布的内容，不仅核对某一个静态 SHA。
